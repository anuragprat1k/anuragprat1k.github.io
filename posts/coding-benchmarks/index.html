The Coding Benchmarks We Optimize For

April 25, 2026

1. Why this post#

“How good is this model at code?” is the wrong question. The right one is: which slice of coding work, under which conditions, with which feedback loop? The answer determines which benchmarks you trust, which you ignore, and what your model becomes when you train against them.

This is a working note on the benchmarks I find load-bearing for a frontier coding model, what each one is actually measuring, and where I think the public eval suite still has blind spots.

2. A taxonomy that I find useful#

I group coding evals along two axes: horizon (how many turns of reasoning and tool use a task spans) and fidelity (how close the task is to what an engineer actually does on the job).

Horizon → Fidelity ↓ Single-turn Multi-turn / agentic
Synthetic HumanEval, MBPP, EvalPlus, APPS LiveCodeBench-Agent, BigCodeBench
Real-world CanItEdit, RefactorBench, SWE-bench Lite SWE-bench Verified, Terminal-Bench, Aider polyglot, METR RE-Bench

Most public attention sits in the bottom-right quadrant now, and rightly so — that’s where the work lives.

3. What each category actually measures#

3.1 Function-level synthesis (HumanEval, MBPP, EvalPlus)#

Cheap, fast, almost saturated. Useful as a smoke test and for tracking regressions in basic code generation, but leakage is endemic and the scores compress at the top. I treat these as a sanity floor, not a signal of capability.

3.2 Competitive programming (CodeContests, LiveCodeBench, USACO)#

These probe pure algorithmic reasoning under hard constraints — tight time/space budgets, adversarial edge cases. LiveCodeBench’s rolling cutoff is the reason it’s still useful; everything older has bled into pretraining. A high score here predicts that the model can hold a complex algorithm in its head, which transfers to debugging gnarly code paths but not to repository navigation.

3.3 Repository-scale SWE (SWE-bench Verified, SWE-bench Multilingual)#

The benchmark that changed how I think about coding evals. A real GitHub issue, a real repo, and a hidden test suite. The model has to read code it didn’t write, localize the bug, and produce a patch that passes. Verified strips out underspecified tasks, which makes the signal much cleaner. The Multilingual variant matters more than people realize — performance does not transfer uniformly across languages.

3.4 Agentic and terminal-driven (Terminal-Bench, SWE-agent harnesses)#

Here the model drives a shell. It runs commands, reads stderr, edits files, runs tests, and iterates. This is the closest public analog to the inner loop of real engineering work, and it’s the regime where scaffolding choices (tool design, context management, retry policies) interact heavily with the underlying model. A 5-point swing from a better harness is common, which makes apples-to-apples comparisons hard.

3.5 Editing and refactoring (CanItEdit, Aider polyglot, RefactorBench)#

The unsung category. Most production model use is editing, not greenfield synthesis — and editing has different failure modes: diff fidelity, preserving unrelated code, respecting the surrounding style. Aider’s polyglot benchmark in particular catches models that generate plausible code that doesn’t apply cleanly.

3.6 Long-horizon (METR RE-Bench, GAIA-style ML tasks)#

Tasks that take a competent human hours to days. These are still early and noisy, but they’re the only public probe for a property I care about a lot: does the model’s competence degrade gracefully as the task gets longer, or does it collapse?

4. What we actually weight, and why#

A model trained to maximize HumanEval is not the model you want. A model trained to maximize SWE-bench Verified is closer, but still not it. Concretely, the properties I want a coding eval suite to jointly reward:

  1. Editing accuracy over synthesis flair. A patch that applies cleanly and changes only what it should beats a more elegant rewrite that touches twenty unrelated lines.
  2. Tool-use efficiency. Solving a SWE-bench task in 12 turns is better than solving it in 60. Step count is a proxy for cost, latency, and how much the model is thinking versus thrashing.
  3. Calibrated uncertainty. A model that runs grep, reads the failing test, then writes the fix is doing the right thing. A model that writes the fix immediately and is right 70% of the time is worse than it looks — the 30% failures are silent and confident.
  4. Long-horizon stability. Performance on a 60-step task should not be (success rate on a 5-step task)^12. If it is, you have a model that needs a babysitter.
  5. Cross-language transfer. Most evals are Python-heavy. A model that drops 20 points on Rust or Go is not a general coding model, it’s a Python model with a costume.
  6. Contamination resistance. Anything with a fixed test set older than the pretraining cutoff is suspect. Rolling benchmarks (LiveCodeBench) and held-out internal sets are the only honest signal at the frontier.

The weighting is not uniform and not static. As scores on a benchmark saturate, its marginal information goes to zero, and the weight should follow.

5. What public benchmarks still miss#

A non-exhaustive list of things I do not yet know how to measure well:

  • Greenfield design. SWE-bench gives you a repo and a bug. Nothing public gives you a blank directory and a product spec.
  • Cross-repo and cross-service work. Real changes often span a service, its client SDK, and a config repo. Single-repo benchmarks miss this entirely.
  • Knowing when to stop. A model that correctly identifies “this requires a design decision, please confirm” should be rewarded. Today’s benchmarks penalize it (no patch = no points).
  • Code review. Reading a diff and finding the bug is a different skill from writing the fix. There is almost no public eval for it.
  • Working with broken tooling. Flaky tests, missing dependencies, half-written CI — the texture of real codebases is absent from curated benchmarks.

6. Where I think this goes#

The next generation of coding evals will be longer, dirtier, and harder to game. Longer because the interesting capability gap is now in multi-hour work, not multi-turn. Dirtier because the realism gap between a curated SWE-bench task and a real on-call ticket is large and matters. Harder to game because static test sets are a contamination risk by construction; the field is moving toward live, rolling, or held-out evaluations as the only credible benchmarks at the frontier.

If a coding eval is cheap to run, easy to interpret, and stable over a year — it’s almost certainly already saturated, or about to be. The benchmarks worth optimizing for in 2026 are the ones that are expensive, noisy, and uncomfortable to look at. That is the signal.
